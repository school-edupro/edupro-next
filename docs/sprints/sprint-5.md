## Decisions taken in the sprint

1. **Step-up is a fresh sign-in, not a second factor prompt of our own.** One Auth owns the factors; the BFF asks for `acr_values` with `max_age=0` and the API trusts `auth_time`. The development bypass accepts `auth_time` and `mfa` overrides so the rule is testable.
2. **Impersonation tokens (`imp.`) and compatibility tokens (`compat.`) share one HS256 verifier with distinct secrets and issuers**; the session row is authoritative so ending a session takes effect on the next request.
3. **Break glass is a real assignment** so the ordinary permission, audit and cache machinery applies; only the event table, the four-hour cap and the report are new.
4. **Security alerts are computed in the API process** as well as in Prometheus, so a school administrator sees them in the admin app without a monitoring stack.
5. **The BFF became a package** (`@edupro/bff`) for the new apps; the admin app still carries its own copy and moves in Sprint 6.
6. **Rate limit is configurable** (`RATE_LIMIT_PER_MINUTE`) because the local load test hit the 600 per minute default with one token.

## Local performance baseline

Measured with `pnpm perf:local` (autocannon, 50 connections, 10 seconds) against the development API on this laptop with the seeded database; numbers are a smoke baseline, not the staging result.

| Endpoint                         | Requests per second | p50   | p95   | p99   | Errors |
| -------------------------------- | ------------------- | ----- | ----- | ----- | ------ |
| `GET /me`                        | 3,409               | 13 ms | 25 ms | 31 ms | 0      |
| `GET /academics/classes?size=50` | 2,493               | 18 ms | 28 ms | 33 ms | 0      |
| `GET /people/search?q=sharma`    | 1,744               | 25 ms | 41 ms | 46 ms | 0      |

All three stay far inside the targets of the k6 script (p95 under 200 ms, 300 ms and 200 ms) at 50 concurrent connections on one laptop; the 200-user run on staging will set the reference numbers.
