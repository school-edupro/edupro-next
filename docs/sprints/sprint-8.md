## 2. Data model and permissions

- Migration `0018_sprint8_admissions_fees.sql`: 16 tables, 5 enums, 3 routines (`app.next_application_no`, `app.generate_fee_demand`, two SECURITY DEFINER public lookups `app.public_admission_schools`, `app.public_school_id`), all tenant tables under forced row-level security. The public lookups join the ADR-006/009 list.
- Permissions: `admissions.cycle.view|manage`, `admissions.application.view|review`, `fees.master.view|manage`, `fees.profile.manage`, `fees.demand.view|generate`. New template role **Accountant** (fee masters, profiles, demands, student view, withdrawal clearance). Academic Coordinator reviews applications; Auditor reads.
- Identity: applicants are not EduPro users. `ApplicantGuard` verifies `Bearer app.<jwt>` (issuer `edupro-applicant`, two hours) and every public handler is on the reviewed public allow-list of the permission-coverage test.

## 4. Decisions

- Proof of work instead of a third-party CAPTCHA: no external dependency, no personal data leaves the app, and the cost (a few hundred milliseconds in the browser at difficulty 4) is enough to stop naive scripts; the difficulty is an environment setting and can be raised under attack.
- OTP delivery through the notification service arrives with Sprint 10; until then the code is logged and, under the development bypass only, returned in the response so the demo works without an SMS provider.
- One `daily` shape for the form: the schema lives on the cycle as JSON; field-level editing in the admin UI is deferred to Sprint 9 (the default form covers the legacy registration fields).
- The demand routine keeps rows with payments and regenerates the rest, mirroring the legacy "define fee" behaviour without the non-atomic writes.
