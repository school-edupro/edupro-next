# Threat model: payments, workflow and attendance ingestion (Sprint 9)

Scope: payments v0 (`apps/api/src/modules/payments`), the workflow engine v0 (`modules/workflow`), admission
decisions (`modules/admissions/decisions.service.ts`) and attendance with RFID ingestion (`modules/attendance`).
Method: STRIDE per trust boundary, mitigations mapped to code and tests. Builds on
`03-threat-model-platform-identity.md` and `04-threat-model-people-academics.md`.

## 1. Trust boundaries

| Boundary                                               | Notes                                                                                                                                                                |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1 Applicant browser → public app → API                | Applicant token (S8). The public app never sees the PayU salt; the API builds the signed request and the browser posts it to the gateway.                            |
| B2 Gateway → API (`/payments/payu/webhook`, `/return`) | Unauthenticated network callers. Trust comes only from the sha512 signature over the PayU field set with our salt, plus amount and status checks against the intent. |
| B3 Gate reader → API (`/attendance/rfid/events`)       | Unauthenticated network callers with a per-device key; the reader posts tag and time only.                                                                           |
| B4 Staff → API (inbox, admit, offline payments)        | Bearer identity + tenant + permission guards, as everywhere.                                                                                                         |

## 2. Threats and mitigations

| Id  | Threat (STRIDE)                                              | Mitigation                                                                                                                                                                                                  | Evidence                                                   |
| --- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| P1  | Forged success notification (S, T)                           | `verifyResponse` recomputes the PayU response hash with the salt and compares in constant time; failures are recorded as `webhook_rejected` events and never change the intent.                             | `admission-to-enrolment.e2e-spec.ts` "forged notification" |
| P2  | Replay of a genuine notification (T, E)                      | `payment_webhooks` is unique on (provider, external id); a second delivery is answered `duplicate` and logged as `replay`, the intent is untouched.                                                         | same spec, "replay returns duplicate"                      |
| P3  | Amount tampering at the gateway page (T)                     | The webhook amount must equal the intent amount to the paisa; otherwise `mismatch`, event recorded, intent unchanged, admit stays blocked.                                                                  | same spec, "tampered amount"                               |
| P4  | Cross-tenant intent lookup from an unauthenticated route (I) | The only cross-tenant read is `app.payment_intent_lookup(txn_id)` (SECURITY DEFINER, returns school id + intent id); everything else runs inside the tenant transaction. Listed in ADR-009.                 | migration 0019; `permission-coverage.spec.ts` allow-list   |
| P5  | Guessable transaction ids (I, E)                             | `txn_id` = timestamp base36 + 64 random bits; globally unique. Knowing an id lets a caller redirect to the gateway for that intent, never read it.                                                          | `payments.service.ts` `createIntent`                       |
| P6  | Mock gateway reachable in production (E)                     | `PAYU_MODE=mock` and the dev key or salt are refused by `env.ts` when `NODE_ENV=production`; `/payments/payu/mock` answers 404 unless the mode is mock.                                                     | `env.ts` production checks                                 |
| P7  | Salt or key leak through logs or the client (I)              | The salt lives only in the API environment; the form sent to the browser carries the request hash, never the salt; PII redaction covers `payerEmail`/`payerMobile` in logs.                                 | `gatewayForm`                                              |
| P8  | Double allocation of an offline payment (T)                  | `app.allocate_fee_payment` runs once inside the recording transaction, allocates oldest dues first and returns the unallocated remainder; the payment row carries the receipt reference for reconciliation. | spec "offline fee payment"                                 |
| W1  | Acting on a step one is not assigned to (E)                  | `act` refuses unless the caller is in `assignee_user_ids` of the current pending step (`workflow.not_assignee`, 403), in addition to `workflow.inbox.act`.                                                  | spec "wrongUser" case                                      |
| W2  | Two open approvals for the same entity (T)                   | Partial unique index on open instances per definition and entity (`workflow.already_pending`).                                                                                                              | migration 0019                                             |
| W3  | Completion handler bypass (T)                                | Handlers run inside the same transaction as the final step; a failure rolls back the decision, so an offer never exists without an approved instance.                                                       | `WorkflowService.act`                                      |
| A1  | Admission without payment (T, E)                             | `admit` requires `selected` and `fee_paid_at` unless `waiveFeeCheck` is set by a holder of `admissions.application.admit` (audited with the flag).                                                          | spec "admission.fee_pending"                               |
| A2  | Seat overbooking (T)                                         | The section with the most free seats in the cycle year is chosen inside the transaction; `app.enrol_student` enforces capacity and one active enrolment per year.                                           | Sprint 6 routine, spec "enrolment"                         |
| R1  | Fake gate posting presence (S, T)                            | Device key is issued once, stored as sha256 and compared in constant time; unknown school or device answers 401; ingestion is throttled per IP like the public routes.                                      | `attendance.e2e-spec.ts` "wrong key"                       |
| R2  | Replayed or duplicated taps (T)                              | Same tag, direction and device within 60 s is a `duplicate`; the first IN of the day decides P or L; a manual mark is never overwritten (`manual_kept`).                                                    | same spec, outcomes                                        |
| R3  | Reader posting for another school (I, T)                     | `app.rfid_device_lookup(school_code, device_code)` is the only cross-tenant lookup; the ingestion then runs inside that school's tenant context.                                                            | migration 0019                                             |
| R4  | Marking outside one's assignment (E)                         | Class teachers with `can_mark_attendance` mark day sessions; subject teachers only their subject; coordinators and admins by scope. Locked sessions refuse edits (`attendance.locked`).                     | same spec                                                  |
| R5  | Absent alerts to the wrong guardian or twice (I)             | Alerts go to the primary guardian's mobile through `MessagesService`; `alert_sent_at` prevents repeats.                                                                                                     | same spec "never twice"                                    |

## 3. Residual risks

- PayU test and live modes are wired but have not been exercised against the real gateway (no merchant account in this environment); the request and response hash formats follow PayU's published field order and are unit-tested against the mock.
- Reader clocks are trusted for `at`; a skewed device can post late arrivals as on time. Server receive time is stored next to it for reconciliation.
- Offline receipts are not yet numbered per school (Sprint 10 fee collection counter).
